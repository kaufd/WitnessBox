## Entries after the move

The numbering continues the decision log kept outside the public repository (D1–D18).

### D19. Machine-readable gate result and the boundary of the supported interface
The gate result existed only in the exit code and `gate.md`, while `report.json` describes only the checker: the checker could pass while tests failed. CI and an external orchestrator need one parseable document. The gate writes `gate.json` (format 1) for every outcome, including early refusals, if the results directory is available. The write is atomic, and if writing is impossible the file is deleted, so a stale PASS does not remain. This is a result document, not a Runner API or an event stream. At the same time the boundary of the supported interface and the versioning policy were fixed (`docs/usage.md`). The distribution was raised to `0.3.0` because a supported format was added. Deferred until a real consumer appears: a separate example of full integration (the path wheel → test.sh → PASS → defect → FAIL already passes in `tests/gate`), a release check on Linux, and separating the recording from enabling the recording in the TypeScript SDK.
(2026-10-31, status: accepted.)

### D20. Shared SDK format and rejection of inexact values in TypeScript
The Java SDK rejected values that cannot be written exactly, while TypeScript passed them to `JSON.stringify`: `NaN` became `null`, an `undefined` field disappeared, a `Date` turned into a string. The same evidence failed in Java and silently lost data in TypeScript. Now TypeScript rejects fractions, `NaN`/`Infinity`, unsafe integers, `undefined`, array holes and non-plain objects with a `TypeError` and the field path; `null` is legal. The error is visible to the test and in the asynchronous `traced()`: a derived `Promise` is returned, rejected with the recording error. The Java SDK does not change, so that the pinned copies in projects do not diverge. The remaining differences (Java `long` is wider than JS safe integers, the `\b`/`\f` bytes, lone surrogates) are described in `docs/sdk.md` together with the conditions for disabling recording in each SDK. One golden scenario, `tests/sdk/golden.jsonl`, is compared byte for byte for Java and TypeScript. Its field order does not become a requirement for other evidence. Dart joins the golden at the first change to the Dart SDK. The change is part of the still unreleased `0.3.0`. Projects with a pinned copy of `ebt.ts` need to update it from the installed distribution.
(2026-10-31, status: accepted; reviewer clarifications incorporated.)

### D21. Rules without Python: the `rules` core checker
The cost of integrating a project is mostly Python checkers (130–400 lines per project), about half of which check the shape of the evidence, while the logic is most often a decision table. A pilot (materials outside the public repository) rewrote the news-window rule of a TypeScript project as tables in `spec.toml`: on 2156 evidence variants the outcome and the partitions matched the Python checker, and the end-to-end report matched together with the self-test. So the core got a `rules` checker: a field schema, consistency, `let` computations, rules in order with a mandatory final `when = "true"`, extra partitions, and `rules_of` for the observation-level twin. Expressions are a subset of Python, parsed by `ast` against an allowlist, with five functions. The tables are validated when the spec is loaded (code 2). The independence of the checker is ensured by the format: a table cannot import application code. The limit was accepted deliberately: there are no generators, lambdas or aggregates with an expression. Anything more complex than a table stays a Python extension, so that the format does not become a second programming language. The name `rules` is now taken by the core. The `spec.toml` format was extended compatibly; the distribution is `0.4.0`.
(2026-11-01, status: accepted at the owner's request to refine the format after the pilot.)

### D22. The `rules` format extended for a second rule
The second rule, a proposal to derive the time balance of a Dart project (78 lines of Python), could not be expressed by the first format. The balance is an integer or the label `"none"`, directions are a list from an enumeration without repeats and without regard to order, and partitions are mappings of values to labels. Only data constructs were added: `also` for labels beyond the type, `list = { enum }` with `unique` and `unordered` (compared as a set, including in `expect`), literals of lists, tuples, sets and dictionaries, and the conditional expression `a if c else b`. Unknown keys in a field schema are a spec error. There are still no generators, lambdas or new functions. The table is 52 lines. On 67,200 evidence variants (640 acceptance records and schema corruption) the outcome and all 20 partitions matched the Python checker, and the end-to-end report matched together with the self-test and known. In 1280 variants the project's Python checker fails with a `TypeError` (a dictionary or a list in `calc_mode`), while the table answers with a WitnessError. It is part of the still unreleased `0.4.0`.
(2026-11-01, status: accepted.)

### D23. The `rules` condition language removed, the field schema remains
D21 and D22 introduced the `rules` checker, but the evaluation after two rules showed that the pilot proved equal verdicts, not a benefit. The `when`, `let` and `expect` conditions are a subset of Python in TOML strings: whoever writes them could write a function, but without highlighting, hints and debugging. The saving in lines is small (57 versus 40 lines of a function with helpers, 52 versus 78), the format was already being extended at the second rule, and supporting it as a spec interface is permanent. Sums, time and concurrency stay Python anyway, and a project would have two ways. The independence argument is weak: a Python checker cannot import Dart, TS or Java application code anyway.

The real benefit of the pilot is the field schema: it replaced about half of every `checks.py`. So `require`, `let`, `rules`, `parts`, `rules_of`, the expression language and the `rules` checker were removed, and the `fields` table became common: the core validates the shape of the evidence before any checker (`WITNESS_MALFORMED`) and passes it the coerced fields, and the schema is validated when the spec is loaded (code 2). The `0.4.0` distribution was never released, so compatibility with `rules` is not needed. The pilot with its own engine is kept outside the public repository. It is worth returning to declarative logic if an author or approver of rules appears who is not a programmer, or a project with dozens of similar simple rules, and then more likely as a table of "input → expected result" examples, without expressions.
(2026-11-01, status: accepted; supersedes D21 and D22 as to the condition language.)

### D24. The `fields` field schema removed, the core returned to 0.3.0
After D23 the field schema became the only remnant of the pilot, and its benefit was measured on a copy of a TypeScript project: `checks.py` is 36% shorter, but with the tables in the spec only 9% shorter, because the OBS twins repeat the schema. The cost, however, is permanent. Knowledge of a rule is split between `spec.toml` and `checks.py`: from the checker code it is not visible which fields are already checked. The core changes data implicitly (releases arrive as dictionaries, `unordered` lists as sets), and editing the schema silently changes what the checker receives. When a field changes there is one more edit, and the spec approved by a human (D4) fills up with technical types. No project uses the schema.

So `schema.py`, the `fields` table and its documentation were removed. The runtime, the tests and the version match the accepted `0.3.0` distribution (commit `ab51640`); version `0.4.0` was not released. Shape validation stays in the checker code next to the rule. If new projects start copying the same shape helpers again, they should be provided as ordinary functions in `ebt_verification.api`, without a second source of truth and hidden conversions, and only at a project's request. The `rules` pilot and the schema measurement are kept outside the public repository with their copies of the engines.
(2026-11-01, status: accepted; supersedes D23 as to the field schema.)

### D25. `traced()` is not introduced in Java and Dart, Dart joins the golden
To reduce the cost of integration, `traced()` was implemented in Java and Dart under a shared contract: `traced : (inv, req, fn: A → R, witness?: (A, R) → Data) → (A → R)`. It was then checked on integrated projects, and the change was rolled back before commit. No project calls `traced()`, even in TypeScript, where it has existed for a long time. TypeScript and JVM projects write evidence at the observation level: the test records what it fed in and what it saw on the output, and there is nothing to wrap. In the Dart project `ev()` sits in domain code and in the test loop; there `traced()` would remove the `scope` boilerplate and the `ok` expression, but `witness` would take as many lines as the current `data`. The default input fields (`Map`) did not fit any candidate: inputs are strings, data classes and models. There are no asynchronous candidates.

The cost, however, is permanent. A mandatory `traced()` makes integrating each new language more expensive, and changing `Ebt.java` and `ebt.dart` would give `pinned_drift` in JVM and Dart projects without benefit to them. So the language-independent contract remains the core: `ev()`, the record format, the permitted values and the shared `tests/sdk/golden.jsonl`. Dart now passes this golden byte for byte together with Java and TypeScript (`make test-dart` in `make test-sdk`, run with and without assert) without changing `ebt.dart`. `traced()` in TypeScript stays an optional convenience: removing it would be an incompatible change without benefit. It is worth returning to `traced()` for another language when a project has a pure function for which a manual `ev()` is noticeably more expensive than a wrapper. The cost of integration should be reduced further by measuring its parts per project (spec, checker, `test.sh`, tests with evidence), not through SDK calls.
(2026-11-01, status: accepted.)

### D26. Snapshot of verification inputs and distribution check after the tests
The gate runs `prepare.sh` and `test.sh` with its own privileges. Experience showed that `test.sh` got PASS on a knowingly wrong result in two ways: by rewriting `spec.toml` and `checks.py` in its directory, or by appending to the installed `checkers.py`. In the second case `gate.json` showed the previous `checker.sha256`, and the following runs of all projects went with the changed checker. Now, before `prepare.sh`, the gate copies `spec.toml`, `checks.py`, `known.toml` and `baseline.jsonl` to `<run-dir>/inputs/`; the checker reads the copy, and `spec_sha256` and `gate.md` describe it. After the tests the originals are compared with the copy, and the installation description (`--installation` with the gate and checker SHA) and an explicit `EBT_CHECK` are compared with those taken before the run. A mismatch is an ERROR with the reason `gate_error`, like a HEAD change during the run. The new `inputs` element in `files` is a compatible change to format 1.

This is detection, not a boundary. Project code runs as the same user and can bypass the check deliberately: change the interpreter or the code of the check itself, leave a background process, persist in the environment until the next run (`~/.gitconfig`, `PATH` directories). The check does not see installation corruption done before the run: comparing `gate_sha256` and `checker_sha256` with the release values is up to the caller. Terminating the process group after the tests was rejected: it is bypassed with `setsid`, and for consumers it would stop Gradle daemons. A permission boundary, a separate OS user or a disposable container for `prepare.sh` and `test.sh`, is deferred until protection against a deliberate attack is needed. The change is part of the still unreleased `0.3.0`.
(2026-11-01, status: accepted.)

### D27. The Dart SDK rejects inexact values, the header without an unverified promise
After D20 Java and TypeScript rejected values that cannot be written exactly, while Dart silently turned a `DateTime` into an ISO string, an enum into its `name`, any other object into its `toString()`, and let fractions through. The same evidence was written in Dart and failed in Java and TypeScript. In addition, the `ebt.dart` header claimed that in release/profile the call together with its arguments is stripped by the compiler; this was not verified. Both fixes were made in one substantive change to `ebt.dart`, because any change to it gives consumers `pinned_drift` (D25).

Now Dart accepts in `data` only `null`, `bool`, `String`, `int`, `List` and `Map` with string keys of those. Everything else raises an `ArgumentError` with the field path (`data.v[0].x`) before `seq` is incremented: neither the log, nor `seq`, nor DevTools changes. `double` is always rejected, on the VM and for `1.0`; on web `int` and `double` are one JS number, so `1.0` is written there as `1`, and a fraction is rejected. The `int` limit on the VM is 64 bits, like Java `long`; on web only ±(2⁵³−1) is exact, and the SDK does not check this. The header now says only what was verified: in release and profile `assert` is not executed, and neither the call nor the evaluation of the arguments happens; removal of code and data from the binary was not verified. The golden `tests/sdk/golden.jsonl` did not change, and Dart still writes it byte for byte.

Consequences for the Dart project. The replay of the pilot's first task in its plural-forms test writes `'value': n` for `[0, 1, 1.0, 2, 5, 0.5, 1.5, 2.5]`: for `1.0`, `0.5`, `1.5` and `2.5` there will now be an `ArgumentError`, the first such record will interrupt the test, and the gate will give FAIL on tests. The class `one_double` in its spec distinguishes `1` and `1.0` by number type; this distinction can be passed as a string (`'value': n is int ? n : '$n'`) with parsing of the decimal string in `_num` of the project's checker, and the spec does not change. The replay of the pilot's second task writes only `int`, `bool`, `String` and enums through `.name`, so its records are not affected. Both replays will get `pinned_drift` until their copy of `ebt.dart` is updated from the installed distribution. The change is part of the still unreleased `0.3.0`.
(2026-11-01, status: accepted.)

### D28. Fractions, time and concurrency are conventions on top of the format, not new types
The `data` format has no fractional numbers, time or order of concurrent operations. This limits rules about money with rates, deadlines and races. It was decided not to extend the format. After D20 and D27 the three SDKs write the same value identically byte for byte (shared golden), while `double`, `BigDecimal` or `DateTime` in the format would break this. Java and JS print some `double` values differently, and automatic serialization in the SDK is a hidden conversion, which was rejected in D24. Any SDK change also gives consumers `pinned_drift` (D25) and adds no precision.

Instead, `docs/sdk.md` fixes conventions on top of the already permitted strings, integers and structures. Money is integer minimal units with a currency, and when they are not enough (rates, exchange rates, precision above 2⁵³) a decimal string. The checker computes it through `decimal.Decimal` in the rounding mode that the requirement names. Non-monetary fractions are a string, and the checker compares them with a tolerance from the spec, not as strings. Time is integer milliseconds since the epoch or ISO-8601 with an offset, a date is `YYYY-MM-DD`, a duration is integer ms, a time zone is an IANA name. Time on which a decision depends is recorded by the application in `data`: the checker does not read the clock. A concurrent scenario is recorded by the test as one piece of evidence: the initial state, the operations with their outcomes and the result. The checker looks for a sequential order that explains these outcomes. The checker still checks each record separately.

The format, the SDK, the golden and the runtime do not change, and there are no new dependencies. Parsing helpers (`Decimal`, time) will appear in `ebt_verification.api` only at a project's request, as agreed in D24. A cross-record checker over a group of `scope` records should be considered in a separate decision, when several projects start copying an aggregated piece of evidence or when a scenario does not fit in one record. A fraction in the format only if a rule appears where a string with a tolerance is not enough.
(2026-11-01, status: accepted.)

### D29. Observation level with a default observation contract, mutation audit as research
Only what is recorded is checked. If a decision is made in two places and the record is in one, coverage by invariant and partitions is closed by records from the first place, and the gate is silent. The proposal, an observation level (D17) by default plus a mutation audit, passed review on a condition: do not promise "the hole is closed" and "the decision is proven", but compare the levels on identical defects. A pilot on a copy of a replay clone of the pilot's TypeScript task (materials outside the public repository) gave:
- of five given defects (a second path, a change after `ev()`, an unapplied decision, an extra record, a flickering window) the decision level found none, OBS found four, OBS with a window-appearance log found all five;
- among 124 mutants of the application code, the decision level found 1 violation, OBS found 57 violations and 12 holes;
- 9 mutants of order boundaries were found only by the decision level;
- of 55 survivors, 24 are session logic. In three of the four checked by a probe, the window returns at the next step of the same session, while the OBS scenarios have already ended by then.

Accepted. For requirements with a visible or persisted outcome, new projects get `<INV>-OBS` by default; the Dart project is not switched (owner's decision of 2026-10-29). The decision level remains for boundaries and as an integrity check on the record. The analyst, besides fields and helpers, writes an "Observation contract" for each `-OBS`: the observation boundary; required and forbidden transitions (a log of appearances, if a wrong state can appear and disappear before the record); the moment the scenario completes and the next steps of the same session; forbidden side effects (a call log of fakes, if the effect does not return to observable state). The role texts are kept in the QA workflow outside the public repository. The logs are project observation helpers verified through `pinned.txt`; the SDK, the format, the core checker and the runtime do not change.

The guarantee is worded this way: OBS checks observable consequences in the given scenarios; a mutation audit detects part of the blind spots of this check. "Mutant killed" means sensitivity to this corruption on these scenarios, not that the decision is proven. A surviving mutant is a candidate for analysis, not a ready conclusion. The percentage killed is not equal to the share of decisions with evidence.

The mutation audit is not part of the gate. Runs are expensive: for 201 mutants it is 10 minutes in 4 threads and about 6% noise under parallel load; labeling the survivors is manual. Automatic operators do not generate temporal states and step sequences, so defects must be given for them. The audit is applied as research on one requirement with classification of outcomes: a checker violation, a coverage or shape hole, a test failure, a launch error, survival. The session gaps in the pilot task are a finding for the project, not a product error. New scenarios and fields in its `spec.toml` are approved by a human (D4). A new Runner API and a mandatory `ev()` in every function were rejected.
(2026-11-01, status: accepted.)

### D30. OBS by default is fixed in the role launch, the action log is read after it
The review of D29 found two shortcomings. First: "OBS by default" was only declared. `run_role.py` (QA workflow) still substituted the OBS texts only with `obs = true`, and the procedure for a new project did not require it. While fixing this it turned out that the `obs.toml` texts are described only for TS: simply enabling by default would have given a Dart project TS instructions. So `obs.toml` lists the languages with a description (`langs = ["ts"]`). Without the `obs` key the observation level is enabled for these languages. A project in another language must explicitly set `obs = false` with a reason in a comment, otherwise the role launch is a refusal (code 2). `obs = true` for a language without a description is also a refusal. The Dart project got an explicit `obs = false` by the owner's decision of 2026-10-29; the TypeScript project does not change. The new-project procedure in the QA workflow requires OBS and allows opting out only with a reason.

Second: in the pilot the closing log was read before the closing. A window that flickered during or after closing did not get into the closing evidence, and in a scenario that ends with the closing nobody checked it. The pilot was repeated with a log that is also read after the action completes (the `appeared_after` field, pilot materials outside the public repository, section 5):
- the defect "window flickers after closing from the feed" was missed by v1 and found by v2 in 4 of 4 closings from the feed;
- the same defect after any closing was seen by v1 only indirectly, from the next show record, and by v2 in 15 of 15 closing records;
- D1–D5 are still caught;
- a window that flickered after 100 ms, that is, later than the completion moment (quiet interval 50 ms), is not seen by v2.

The observation contract in `obs.toml` now requires reading the action's record log after it completes. If the state before the action also matters, the log is read twice. The completion moment is chosen explicitly: a change scheduled later than it is not observed.
(2026-11-01, status: accepted; refines D29.)

### D31. The `ebt/` scaffold in the distribution: spec, `test.sh` per stack and `pinned.txt`
Integrating a new project started with manual copying: `test.sh` repeated the gate contract and `pinned.txt` repeated the SDK path, and mistakes in them were found only by a red run. Open question 1 of the previous handoff required measuring the cost of integration. The scaffold does not replace that measurement and does not reduce SDK calls or checkers, but it removes the repetitive part in which a mistake is visible only on a run. So the distribution gained a scaffold, not a new Runner API or UI.

`resources/scaffold/` contains a common `spec.toml` with an example `[req]`/`[inv]`, an example `checks.py` with `test_checks.py`, `README.md` and one directory per stack (`dart`, `ts`, `jvm`) with `test.sh` and `pinned.txt`. The installed command `ebt-gate --scaffold <dart|ts|jvm> [<ebt-dir>]` copies them into a new directory, makes `test.sh` executable and refuses to write into an existing non-empty directory: it will not overwrite an approved spec. This is the only new CLI behavior; the JSON formats, exit codes, the `test.sh` contract and `pinned.txt` do not change.

The template `spec.toml` is an example, not an approved requirement: the IDs `REQ-EXAMPLE-1`/`INV-EXAMPLE-1` and `example_rule` are replaced, and the spec is still approved by a human (D4). The `test.sh` templates follow the gate contract (`OUT_DIR`, codes 0/1/2, evidence on any outcome) and are designed for macOS `/bin/bash` 3.2. Evidence is collected from `build/ebt/`, as described in `docs/sdk.md`. The scaffold is data for a project, not verification code: its directory is excluded from `gate_sha256`, so editing a template does not change the identity of the installed gate. The scaffold does not create `known.toml`, `baseline.jsonl` and `prepare.sh`: they appear as a project needs them. The change is part of the still unreleased `0.3.0`. Verified by tests of the installed wheel (`make test`): creation for all three stacks, refusal on a non-empty directory, executability and `bash -n`, tests of the checker example, presence of the files in the wheel, and unchanged `gate_sha256` when a template is edited; `make example` does not change.
(2026-11-01, status: accepted.)

### D32. The `ebt/` scaffold: three fixes from review
The review of D31 found three reproducible errors. (1) In `jvm/test.sh`, after `nullglob`, the expression `"$results"/TEST-*.xml` with no matches disappeared, and `grep` without file names read stdin: with an open stdin the script could hang instead of returning code 2. Now the XML reports are first collected into an array, and an empty array gives 2 immediately. (2) `test_checks.py` suggested `python3 -m unittest`, but after `uv tool install` the package sits in the tool's environment, and the system `python3` does not see it. The scaffold's instructions and README now take the interpreter from `ebt-gate --installation` (the `python` field); the system `python3` in that command only reads JSON. (3) `ebt-gate --scaffold ts .` failed with `Invalid argument: '.'`: a temporary directory was created inside `.`, then the code tried to remove `.` itself. The destination path is now normalized before the temporary directory is created, and an existing empty directory (including `.`) is filled in place, without `rmdir`.

Targeted tests were added: JVM without XML with an open stdin (code 2, no hang), running the checker example exactly as the instructions in `test_checks.py`/README say, and `--scaffold ts .` in an empty directory. The other contracts of D31 do not change; the change is part of the still unreleased `0.3.0`.
(2026-11-01, status: accepted; refines D31.)

### D33. Release 0.3.0
Distribution `0.3.0` is released: tag `v0.3.0` is on commit `981e7f4`, from which the artifacts were built and checked. This entry was added by the next commit, because `docs/` is part of the sdist and an entry containing its hash cannot lie inside it. The distribution includes D19–D32: `gate.json` format 1, the shared SDK golden for Java, TypeScript and Dart, SDK rejection of inexact values, the snapshot of verification inputs and the `ebt/` scaffold. Before the tag, on the final code, the following was checked:

### D43. Self-test by list elements
One "kill" per field was not enough: the self-test corrupted only the first scalar value inside a field, so a checker that reads `items[0]` and ignores the other elements passed the check. Now the self-test corrupts every list element — the first 8 (`MAX_INDEX`), by deleting the element and corrupting its content — and keeps counters by the full path `field[i]…`/`field.key`. `self_test()` gained `weak_paths` — the sorted paths whose corruption was never caught. `weak_fields` remains for consumers and is now derived from `weak_paths`; `Report.weak_required` lists the paths, and for a scalar field the path equals the field name, so earlier reports do not change. The self-check does not reorder list elements: a checker legitimately compares some lists as a set.

`not_in_verdict` accepts a field name, which covers all of its subpaths, or a path with `[*]` (`lines[*].note`). Concrete indexes are not supported: the path is normalized to `[*]`, so an exclusion does not bind the report to the order of elements.

Consequence: a project can get a new `weak_required` FAIL on a list field. It is cleared by fixing the checker with a targeted test for each element, or by adding the path to `not_in_verdict` after a human approves the requirement (D4). In the demonstration example the self-test found in the correct evidence of `INV-SYNC-1` the `remote` lines whose removal did not change the result. The `sync_merge` checker is right in this, so a correct piece of evidence was added to the example in which every `remote` line affects the result; the check was not weakened for this. The version is `0.6.0`: the report content (`weak_paths`) and the set of paths in `weak_required` change.

A shape rejection is counted separately from a logic kill: `fields[k]` and the path counters gained `rejected` — the number of mutants on which the checker answered `WitnessError`; `killed` keeps its previous meaning (the verdict is not ok or `WitnessError`), so `rejected <= killed`. Paths where all kills are shape rejections (`killed == rejected`) are listed in `shape_only_paths` as information: they do not get into `weak_required` and do not change the verdict. To tell a shape check from a check against the rule, the self-test additionally substitutes the value of a top-level field from the first other sample of the same invariant where it differs (the path is the field name): substituting another permitted value is caught only by logic.

Substitutions are counted separately (`substituted`): a path is weak only if it had ordinary mutants (`tried > substituted`), because a substitution does not create weakness by itself. Otherwise two correct samples that differ in a value that legitimately does not affect the verdict (for example `discount` `fixed:0` and `none:0`, or the same list set in a different order) would give a false FAIL. A substitution affects only `killed` and `shape_only_paths`, and `fields[k]` sums `substituted` as well.
(2026-11-01, status: accepted.)

### D44. `ebt-gate --sync-pinned`
Copies of the SDK were updated by hand after every change of bytes (D27, D36), and the divergence was found only by the gate with the reason `pinned_drift`. The command `ebt-gate --sync-pinned <ebt-dir> [<project-root>]` parses `pinned.txt` the same way as `gate.sh`: empty lines and lines with `#` are skipped, the first token is the original (`kit:` — from the installation resources, absolute — as is, otherwise relative to `<ebt-dir>`), and the second is the path in the project. `<project-root>` defaults to the current directory; the output is `обновлён <dest>` or `без изменений <dest>`, one line per copy. Code `0` means that after execution all copies match the originals; code `2` is an error, nothing is written.

The command only copies the originals per `pinned.txt` and does not change the gate check: `pinned_drift` still means that the pinned copy does not match the original. An absolute destination path, escaping the project root (including through `..` or a symlink), a line with `\r`, and a repeated destination path are rejected: from a CRLF line the gate would read a path with `\r` and look for the copy in the wrong place, and two lines with one path would give a silent overwrite and then `pinned_drift`. All lines are validated before the first write, so that a refusal does not leave half of the copies updated.

### D45. The gate in GitHub Actions: untrusted tests and a trusted re-check
D26 left the verdict and `gate.json` within reach of the code under verification: `test.sh` and `prepare.sh` run as the same user as the gate and can forge the result. D34 bound `gate.json` to the evidence with a hash, but a consistent substitution of the files and the result after the verdict could not be detected. CI needs a verdict issued where project code is not executed, and a signature that binds `gate.json` to the workflow of the main branch.

The check is split into two stages. `ebt-tests` runs on `pull_request` and is untrusted: it installs the verified distribution, runs `ebt-gate` as usual and uploads `out/*.jsonl` and `gate.json` as the `witnessbox-evidence` artifact. Its verdict is information only. `ebt-verify` runs on `workflow_run` and is trusted: GitHub always takes this workflow from the main branch, so the task branch cannot change it. Project code is not executed in the second stage: `ebt/` is extracted from `BASE`, `prepare.sh` is removed, and instead of `test.sh` a replay script is installed that only hands out the evidence from the artifact. The check is performed by the real `ebt-gate`. Then `gate.json` is signed with `actions/attest-build-provenance`, `gate.md` is published in the summary, and the commit status `witnessbox/gate` is set on `head_sha` (`success` — PASS, `failure` — FAIL, `error` — ERROR or a refusal before the gate). The logic is in the composite actions `actions/setup` and `actions/verify`; the witnessbox installation is compared with the `release.json` of the release, and the results of the second stage are uploaded as the `witnessbox-verdict` artifact.

`pull_request_target` with execution of PR code was rejected: it would give the branch code a write token and access to secrets. `workflow_run` does not let the branch change the workflow, because the definition is taken from the main branch. The artifact of the first stage is treated as untrusted: replay copies only regular `out/*.jsonl` files and does not follow symlinks, and `tests_exit_code` is accepted only as the integer 0 or 1; `EBT_REPLAY_DIR` is a second-stage variable. All `uses:` are pinned to a full SHA (for third-party actions, the commit SHA of their repository; for WitnessBox actions, the WitnessBox commit SHA). The runtime and the Runner API do not change.

What is covered: the verdict and `gate.json` are not changed by project code; the signature binds `gate.json` to the workflow of the main branch; the spec and `checks.py` are taken from `BASE`, so an edit of `ebt/spec.toml` in the branch gives FAIL `protected_paths_changed`, not PASS by the branch's spec. What is not covered: the evidence is still written by the code under verification, and `tests_exit_code` of the first stage is a claim of that code, as in a local run; a deliberate bypass in the first stage (a background process, `PATH`, `~/.gitconfig`) is not caught. PRs from forks are not supported in the first version: `workflow_run` has no `pull_requests[].base.sha` for them, so the status is `error`, not `success`. Attestations in private repositories require a GitHub plan that supports artifact attestations.

### D48. The `generic` stack and end-to-end examples in CI

### D47 clarification. The boundary of `--check-only` with the gate (0.7.0 review)
The review of the 0.7.0 branch reproduced six inputs where `--check-only` returned `1` and the gate returned PASS, that is, the guarantee of D47 was violated. The causes split.

An unregistered checker in the spec passed if its invariant had no records or was outside `EBT_INV`: `NO_CHECKER` arose only when a record was checked. Now, before parsing the evidence, `ebt-check` requires every `checker` from `spec.toml` to be in `CHECKERS`; an unknown checker is code `2` (ERROR), not a silent PASS. The check is common to `ebt-check` and `--check-only`; when `EBT_CHECK` is set, `--check-only` does not judge registration by the local registry, because an external checker may know its own checkers.

The other five inputs are strict `read_pinned` checks inherited from `--sync-pinned` that the gate does not make: `\r` or non-UTF-8 in a comment line, an absolute `dest`, a `dest` outside the clone (`../x`), and a repeated `dest` with a matching copy. `--check-only` now parses `pinned.txt` in the `gate_rules=True` mode: comments are skipped before any checks, an absolute and a relative `dest` outside the clone and a repeat are allowed, and only the content is compared. The strict rules stay with `--sync-pinned`: it writes files and must reject an ambiguous path.

The reverse divergences, where `--check-only` answered `0` and the gate answered ERROR, are also closed: a repository without commits (no `HEAD`), an `EBT_CHECK` pointing to a nonexistent command, and an `EBT_INV` with an unknown invariant. All three now give a problem of the corresponding check.

In `generic/test.sh` the command from `EBT_TEST_CMD` is normalized before running: trailing newlines and an end-of-line comment are dropped, and if the command itself refers to `"$@"`/`"$*"`, the words of `EBT_TESTS` arrive as positional parameters and are not added a second time. Test gaps are closed: cases A–F, reverse cases, a check of the evidence in `OUT_DIR` at code `7`, and edge cases of `EBT_TEST_CMD` were added.

`gradle/actions/setup-gradle` in CI was moved from `v6.4.1` (5 days old at the time of review) to `v6.4.0` (2026-09-28), so that the rule "no younger than two weeks" holds. The distribution version stays `0.7.0`: it is not released yet.
(2026-11-02, status: accepted.)

### D47 clarification 2. Checker registration, external `EBT_CHECK` and `generic`
The first clarification of D47 made an unregistered checker a launch error of `ebt-check` (code `2`). This changed the public checker codes and the gate verdict more than necessary: a scenario in which the approved spec already contains an invariant whose checker is not yet written, while the task is limited to another `EBT_INV`, started to give ERROR. This clarification reverses that in favor of a finding in the report.

Now `NO_CHECKER` for an invariant in scope is added to the `build_report` report even before the records are parsed, if it has no records; if there is a record, `check_record` gives the finding. The exit code stays the same: `1` (FAIL) for a critical finding, `0`/`2` do not change. An invariant outside `EBT_INV` with an unwritten checker does not fail the run while there is no record with this invariant; `--check-only` reports such a problem only for invariants in scope. So the scenario "the spec is ahead of the code, the task is in another invariant" works again, and the guarantee "a `--check-only` problem → not PASS" is kept.

With `EBT_CHECK` set, `--check-only` no longer parses `spec.toml`, `checks.py`, `known.toml` and `baseline.jsonl` locally: an external checker may understand them differently, and a local problem would violate the guarantee (verified: a failing `checks.py` with an external checker that answers `0` gave a gate PASS while the hint reported a problem). Only the parts that do not depend on the checker are checked: the presence of `spec.toml`, the existence of `EBT_CHECK`, the runner, `pinned.txt`, the clone and `BASE`; the absence of the external command is a problem.

In `generic/test.sh` the hand-written shell parsing was removed: it did not cover trailing `;`/`&`/`|`/`\`, positional `$1…$9` and complex quoting. Instead of parsing, the command must be simple; if it contains `#`, `;`, `&`, `|`, `\` or `$1…$9`, it must itself refer to `"$@"`/`"$*"`, otherwise `test.sh` returns code `2` with a message. A simple command receives the words of `EBT_TESTS` as separate argv; a complex scenario is written as a script. This closes the class of errors "the argument ran as a separate command / was lost", not individual examples.

`docs/architecture.md` describes `NO_CHECKER` as FAIL, including for an invariant in scope without records. The version stays `0.7.0`.
(2026-11-02, status: accepted.)

### D47 clarification 3. `--allow-uncovered` and argument edge cases
`D47 clarification 2` says that the `ebt-check` codes do not change, but this is not quite true for `--allow-uncovered`: if the scope has an invariant without a checker and without records, before the fix the flag hid the coverage hole and gave `0`, and now `NO_CHECKER` is a critical finding and code `1`. This is a deliberate consequence: a task invariant cannot be considered covered if there is nothing to check it with. The gate does not pass `--allow-uncovered`, so its verdict is not affected; `--check-only` does not know about the flag and reports the problem.

The reverse divergence remains and is not promised by D47: an invariant outside `EBT_INV` with an unknown checker and a record gives the gate `NO_CHECKER` (FAIL), and `--check-only` gives `0`, because it does not read the evidence. Closing it would require changing the gate verdict again or reading the evidence in the hint; neither is part of D47.

In `generic/test.sh`, `${1}…${9}` is additionally closed (before, `$1…$9` caught only the short form), as is `$@` in single quotes: that is a literal, and the arguments were lost. Now such a command without double quotes around `"$@"`/`"$*"` gives code `2`.
(2026-11-02, status: accepted.)

### D48 clarification. `EBT_TEST_CMD` in `generic` without syntax parsing
The clarifications D47 2 and 3 added to `generic/test.sh` recognition of `"$@"`, quotes, `#`, `;`, `&`, `|`, `\` and `$1…$9`. Each review iteration closed the previous edge cases and opened new ones: the last version with a regular expression again let `'$@'` through after a word in double quotes. The check was not worth its complexity: an error in `EBT_TEST_CMD` is almost always visible (an argument run as a separate command gives code 127, the result `2` and a gate ERROR), while a silent loss of the `EBT_TESTS` filter runs more tests but does not weaken the verdict — the checker re-checks the evidence anyway. The gate also passes `EBT_TESTS` without quotes, so words with spaces never reach `test.sh`.

The parsing was removed. `EBT_TEST_CMD` is a simple command, the words of `EBT_TESTS` are appended to its end as separate argv, and only trailing newlines and spaces are dropped (a `|` block in YAML). A complex scenario is written as its own script. This reverses parts of D47 clarifications 2 and 3 concerning `generic/test.sh`.
(2026-11-02, status: accepted.)

### D53. `ebt.dart` is robust to dart format
The Dart project copies `ebt.dart` byte for byte (`pinned.txt`), and its CI may run `dart format --set-exit-if-changed`. The 0.7.0 file stayed unchanged only in the short style at width 80. The tall style (Dart 3.7+) and widths 100–120 joined signatures, getters and calls. The copy cannot be formatted — that is `pinned_drift`, and each project would have to exclude it from the formatter separately.

Accepted: every statement of `ebt.dart` takes one line shorter than 80 characters, and long expressions are split into local variables. Then there is nothing for any style at width 80–120 to join or wrap.
