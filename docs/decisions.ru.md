## Текущий статус

- Продукт — Witnessbox, дистрибутив и пакет `witnessbox`, лицензия MIT (D36, D38); выпущена `0.7.0` (тег `v0.7.0`, PyPI, выпускные SHA-256 — D52): одна команда `witnessbox` (D51), `gate --check-only` и `test-checks` (D47), стек `generic` и сквозные примеры в CI (D48); предыдущая — `0.6.0` (D46): self-test по путям (D43), `sync-pinned` (D44) и CI-режим GitHub Actions (D45). Публичная документация онбординга — [quickstart](quickstart.ru.md) и [authoring](authoring.ru.md) (D49), инструкция для агента-кодировщика — [agent](agent.ru.md) (D50). Публикация — Trusted Publishing из `publish.yml` файлов, проверенных `make release-check` (D40). `gate.json` (D19) привязан к свидетельствам (D34). Чекер `rules` и схема полей `fields` в продукт не вошли (D24).
- SDK: общий golden для Java, TypeScript и Dart, допустимые значения, соглашения для дробей, времени и конкурентности и гарантии отключения записи — [sdk](sdk.ru.md) (D20, D25, D27, D28). Общий контракт языков — `ev()`; `traced()` есть только в TypeScript (D25).
- Граница поддерживаемого интерфейса и правила совместимости — в [usage](usage.ru.md#поддерживаемый-интерфейс-и-совместимость).
- Публичная команда — установленная `witnessbox` с подкомандами `gate` (включая `--check-only`), `check`, `scaffold`, `sync-pinned`, `test-checks` и `spec`; проектный API типов — `witnessbox.api`, совместимый импорт — `ebt_verification.api` (D38, D47, D51, D58). Человек утверждает спецификацию по её странице и `sha256` (D58).
- Чекер независим от кода приложения и SDK. Требования с видимым исходом проверяются и на уровне наблюдения с контрактом наблюдения (D29).
- Границы гарантий и модель угроз — [security](security.ru.md): что гейт обнаруживает и чего не обещает.
- CI-режим — недоверенные тесты `ebt-tests` на `pull_request` и доверенная перепроверка `ebt-verify` на `workflow_run`; подписанный `gate.json` и статус `witnessbox/gate` — [ci](ci.ru.md) (D45).
- `test.sh` — предпочтительный контракт запуска новых проектов; исторический Flutter fallback сохранён для совместимости.
- Новый проект получает заготовку `ebt/` командой `witnessbox scaffold` для `dart`, `ts`, `jvm` или `generic` (D31, D48), а закреплённые в `pinned.txt` копии — командой `witnessbox sync-pinned` (D44); тесты чекера и проверку подключения запускают `witnessbox test-checks` и `witnessbox gate --check-only` (D47, D51). Шаблонная спецификация не является утверждённой.
- Новый Runner API, UI и runtime-зависимости не добавляются без отдельного решения.

История обсуждений, концепции, roadmap и evidence levels ведутся вне публичного репозитория и содержат исходный контекст; эти документы отражают историческое состояние и не являются обещанием будущей реализации.

## Записи после переноса

Нумерация продолжает журнал решений, который ведётся вне публичного репозитория (D1–D18).

### D19. Машиночитаемый итог гейта и граница поддерживаемого интерфейса
Итог гейта был только в коде выхода и `gate.md`, а `report.json` описывает лишь чекер: чекер мог пройти при упавших тестах. CI и внешнему оркестратору нужен один разбираемый документ. Гейт пишет `gate.json` (формат 1) при любом итоге, включая ранние отказы, если каталог результатов доступен; запись атомарная, а при невозможности записи файл удаляется, поэтому устаревший PASS не остаётся. Это итоговый документ, а не Runner API или поток событий. Одновременно зафиксирована граница поддерживаемого интерфейса и политика версий (`docs/usage.md`); поставка поднята до `0.3.0`, потому что добавлен поддерживаемый формат. Отложены, до реального потребителя: отдельный пример полного подключения (путь wheel → test.sh → PASS → дефект → FAIL уже проходит `tests/gate`), проверка выпуска на Linux и разделение записи и включения записи в TypeScript SDK.
(2026-10-31, статус: принято.)

### D20. Общий формат SDK и отказ на неточных значениях в TypeScript
Java SDK отклонял значения, которые нельзя записать точно, а TypeScript отдавал их в `JSON.stringify`: `NaN` становился `null`, поле `undefined` пропадало, `Date` превращался в строку. Одно и то же свидетельство на Java падало, а на TypeScript тихо теряло данные. Теперь TypeScript отклоняет дроби, `NaN`/`Infinity`, небезопасные целые, `undefined`, дыры массивов и объекты не простого вида с `TypeError` и путём поля; `null` легален. Ошибка видна тесту и в асинхронном `traced()`: возвращается производный `Promise`, отклоняемый ошибкой записи. Java SDK не меняется, чтобы закреплённые копии в проектах не разошлись; оставшиеся различия (`long` шире безопасных целых JS, байты `\b`/`\f`, одиночные суррогаты) описаны в `docs/sdk.md` вместе с условиями отключения записи для каждого SDK. Один golden-сценарий `tests/sdk/golden.jsonl` сравнивается байт в байт для Java и TypeScript; порядок полей в нём не становится требованием к другим свидетельствам. Dart подключается к golden при первой правке Dart SDK. Изменение входит в ещё не выпущенную `0.3.0`. Проектам с закреплённой копией `ebt.ts` нужно обновить её из установленной поставки.
(2026-10-31, статус: принято; уточнения ревьюера учтены.)

### D21. Правила без Python: чекер ядра `rules`
Стоимость подключения проекта в основном — Python-чекеры (130–400 строк на проект), примерно половина которых проверяет форму свидетельства, а логика чаще всего — таблица решений. Пилот (материалы вне публичного репозитория) переписал правило окна новостей проекта на TypeScript таблицами в `spec.toml`: на 2156 вариантах свидетельств исход и классы входов совпали с Python-чекером, сквозной отчёт совпал вместе с self-test. Поэтому в ядро добавлен чекер `rules`: схема полей, согласованность, вычисления `let`, правила по порядку с обязательным последним `when = "true"`, дополнительные классы входов и `rules_of` для близнеца уровня наблюдения. Выражения — подмножество Python, разбираемое `ast` по белому списку, с пятью функциями; таблицы проверяются при загрузке spec (код 2). Независимость чекера обеспечена форматом: таблица не может импортировать код приложения. Ограничение принято сознательно: генераторов, лямбд и агрегатов с выражением нет — всё сложнее таблицы остаётся Python-расширением, чтобы формат не стал вторым языком программирования. Имя `rules` теперь занято ядром. Формат `spec.toml` расширен совместимо; поставка — `0.4.0`.
(2026-11-01, статус: принято по просьбе владельца доработать формат после пилота.)

### D22. Формат `rules` расширен по второму правилу
Второе правило — предложение вывода баланса времени проекта на Dart (78 строк Python) — первым форматом не выражалось: баланс — целое или метка `"none"`, направления — список из перечисления без повторов и без учёта порядка, классы входов — отображения значений в метки. Добавлены только конструкции-данные: `also` для меток сверх типа, `list = { enum }` с `unique` и `unordered` (сравнение как множество и в `expect`), литералы списков, кортежей, множеств и словарей, условное выражение `a if c else b`; неизвестные ключи схемы поля — ошибка spec. Генераторов, лямбд и новых функций по-прежнему нет. Таблица — 52 строки; на 67 200 вариантах свидетельств (640 записей приёмки и порча по схеме) исход и все 20 классов входов совпали с Python-чекером, сквозной отчёт совпал вместе с self-test и known. В 1280 вариантах Python-чекер проекта падает с `TypeError` (словарь или список в `calc_mode`), таблица отвечает WitnessError. Входит в ещё не выпущенную `0.4.0`.
(2026-11-01, статус: принято.)

### D23. Язык условий `rules` убран, остаётся схема полей
D21 и D22 ввели чекер `rules`, но оценка после двух правил показала: пилот доказал равенство вердиктов, а не выгоду. Условия `when`, `let` и `expect` — подмножество Python в строках TOML: кто пишет их, напишет и функцию, но без подсветки, подсказок и отладки. Экономия строк невелика (57 против 40 строк функции с помощниками, 52 против 78), формат расширялся уже на втором правиле, а его поддержка как интерфейса spec постоянна; суммы, время и конкурентность всё равно остаются Python, и у проекта было бы два способа. Довод о независимости слабый: Python-чекер и так не может импортировать код приложения на Dart, TS или Java.

Реальная польза пилота — схема полей: она заменяла около половины каждого `checks.py`. Поэтому `require`, `let`, `rules`, `parts`, `rules_of`, язык выражений и чекер `rules` удалены, а таблица `fields` стала общей: ядро проверяет форму свидетельства до любого чекера (`WITNESS_MALFORMED`) и передаёт ему приведённые поля, схема проверяется при загрузке spec (код 2). Поставка `0.4.0` не выпускалась, поэтому совместимость с `rules` не нужна. Пилот с собственным движком сохранён вне публичного репозитория. Вернуться к декларативной логике стоит, если появится автор или утверждающий правил не программист или проект с десятками однотипных простых правил — и тогда скорее как таблица примеров «вход → ожидаемый результат», без выражений.
(2026-11-01, статус: принято; заменяет D21 и D22 в части языка условий.)

### D24. Схема полей `fields` убрана, ядро возвращено к 0.3.0
После D23 схема полей стала единственным остатком пилота, и её выгода измерена на копии проекта на TypeScript: `checks.py` короче на 36 %, но с таблицами в spec — лишь на 9 %, потому что близнецы OBS повторяют схему. Цена при этом постоянная. Знание о правиле делится между `spec.toml` и `checks.py`: из кода чекера не видно, какие поля уже проверены. Ядро неявно меняет данные — релизы приходят словарями, `unordered`-списки множествами, — и правка схемы молча меняет то, что получает чекер. При изменении поля правок становится на одну больше, а утверждаемая человеком spec (D4) наполняется техническими типами. Ни один проект схемой не пользуется.

Поэтому `schema.py`, таблица `fields` и её документация удалены; runtime, тесты и версия совпадают с принятой поставкой `0.3.0` (коммит `ab51640`), версия `0.4.0` не выпускалась. Проверка формы остаётся в коде чекера рядом с правилом. Если новые проекты будут снова копировать одинаковые помощники формы, их стоит дать обычными функциями в `ebt_verification.api` — без второго источника истины и скрытых преобразований — и только по запросу проекта. Пилот `rules` и измерение схемы сохранены вне публичного репозитория со своими копиями движков.
(2026-11-01, статус: принято; заменяет D23 в части схемы полей.)

### D25. `traced()` в Java и Dart не вводится, Dart входит в golden
Чтобы снизить цену подключения, `traced()` реализовали в Java и Dart по общему контракту: `traced : (inv, req, fn: A → R, witness?: (A, R) → Data) → (A → R)`. Затем проверили на подключённых проектах, и правка была откачена до коммита. `traced()` не вызывает ни один проект, даже в TypeScript, где она есть давно. Проекты на TypeScript и JVM пишут свидетельства на уровне наблюдения: тест записывает, что подал на вход и что увидел на выходе, а обёртывать там нечего. В проекте на Dart `ev()` стоит в доменном коде и в цикле теста; там `traced()` убрала бы шаблон `scope` и выражение `ok`, но `witness` занял бы столько же строк, сколько нынешний `data`. Поля входа по умолчанию (`Map`) не подошли ни одному кандидату: входы — строки, data-классы и модели. Асинхронных кандидатов нет.

Цена при этом постоянная. Обязательная `traced()` делает подключение каждого нового языка дороже, а правка `Ebt.java` и `ebt.dart` дала бы `pinned_drift` в проектах на JVM и Dart без пользы для них. Поэтому языконезависимым контрактом остаётся ядро: `ev()`, формат записи, допустимые значения и общий `tests/sdk/golden.jsonl`. Dart теперь проходит этот golden байт в байт вместе с Java и TypeScript (`make test-dart` в `make test-sdk`, запуск с assert и без) без изменения `ebt.dart`. `traced()` в TypeScript остаётся необязательным удобством: удалять её — несовместимое изменение без выгоды. Вернуться к `traced()` для другого языка стоит, когда в проекте появится чистая функция, которой ручной `ev()` заметно дороже обёртки. Цену подключения дальше снижать через замер её частей по проектам (spec, чекер, `test.sh`, тесты со свидетельствами), а не через вызовы SDK.
(2026-11-01, статус: принято.)

### D26. Снимок входов проверки и сверка поставки после тестов
Гейт исполняет `prepare.sh` и `test.sh` со своими правами. Опыт показал, что `test.sh` получал PASS на заведомо неверном результате двумя способами: переписав `spec.toml` и `checks.py` в своём каталоге или дописав установленный `checkers.py`. Во втором случае `gate.json` показывал прежний `checker.sha256`, а следующие прогоны всех проектов шли уже с изменённым чекером. Теперь гейт до `prepare.sh` копирует `spec.toml`, `checks.py`, `known.toml` и `baseline.jsonl` в `<run-dir>/inputs/`; чекер читает копию, `spec_sha256` и `gate.md` описывают её. После тестов оригиналы сравниваются с копией, а описание установки (`--installation` с SHA гейта и чекера) и явный `EBT_CHECK` — со снятыми до запуска. Расхождение — ERROR с причиной `gate_error`, как смена HEAD за прогон. Новый элемент `inputs` в `files` — совместимое изменение формата 1.

Это обнаружение, а не граница. Код проекта работает от того же пользователя и может обойти сверку намеренно: изменить интерпретатор или код самой сверки, оставить фоновый процесс, закрепиться в окружении до следующего запуска (`~/.gitconfig`, каталоги `PATH`). Порчу установки, сделанную до запуска, сверка не видит: сравнивать `gate_sha256` и `checker_sha256` с выпускными значениями должен вызывающий. Завершение группы процессов после тестов отвергнуто: оно обходится через `setsid`, а у потребителей останавливало бы демоны Gradle. Граница прав — отдельный пользователь ОС или одноразовый контейнер для `prepare.sh` и `test.sh` — отложена до потребности в защите от намеренной атаки. Изменение входит в ещё не выпущенную `0.3.0`.
(2026-11-01, статус: принято.)

### D27. Dart SDK отклоняет неточные значения, заголовок без непроверенного обещания
После D20 Java и TypeScript отклоняли значения, которые нельзя записать точно, а Dart молча превращал `DateTime` в ISO-строку, enum — в `name`, любой другой объект — в `toString()` и пропускал дроби. Одно свидетельство на Dart записывалось, а на Java и TypeScript падало. Кроме того, заголовок `ebt.dart` утверждал, что в release/profile вызов вместе с аргументами вырезается компилятором; это не проверялось. Обе правки сделаны одной содержательной правкой `ebt.dart`, потому что любое его изменение даёт потребителям `pinned_drift` (D25).

Теперь Dart принимает в `data` только `null`, `bool`, `String`, `int`, `List` и `Map` со строковыми ключами из них. Всё остальное — `ArgumentError` с путём поля (`data.v[0].x`) до увеличения `seq`: ни лог, ни `seq`, ни DevTools не меняются. `double` отклоняется всегда, на VM и для `1.0`; на web `int` и `double` — одно JS-число, поэтому `1.0` там пишется как `1`, а дробь отклоняется. Предел `int` на VM — 64 бита, как `long` в Java; на web точны только ±(2⁵³−1), и SDK это не проверяет. Заголовок теперь говорит только проверенное: в release и profile `assert` не исполняется, ни вызов, ни вычисление аргументов не происходят; удаление кода и данных из бинарника не проверялось. Golden `tests/sdk/golden.jsonl` не изменился, Dart по-прежнему записывает его байт в байт.

Последствия для проекта на Dart. Replay первой задачи пилота в его тесте множественных форм пишет `'value': n` для `[0, 1, 1.0, 2, 5, 0.5, 1.5, 2.5]`: на `1.0`, `0.5`, `1.5` и `2.5` теперь будет `ArgumentError`, первая же такая запись прервёт тест, и гейт даст FAIL по тестам. Класс `one_double` в его spec различает `1` и `1.0` по типу числа; передать это различие можно строкой (`'value': n is int ? n : '$n'`) с разбором десятичной строки в `_num` проектного чекера, spec при этом не меняется. Replay второй задачи пилота пишет только `int`, `bool`, `String` и enum через `.name`, его записи не затронуты. Оба replay получат `pinned_drift`, пока их копию `ebt.dart` не обновят из установленной поставки. Изменение входит в ещё не выпущенную `0.3.0`.
(2026-11-01, статус: принято.)

### D28. Дроби, время и конкурентность — соглашения поверх формата, а не новые типы
В формате `data` нет дробных чисел, времени и порядка конкурентных операций. Это ограничивает правила о деньгах со ставками, дедлайнах и гонках. Расширять формат не стали. После D20 и D27 три SDK записывают одно и то же значение байт в байт одинаково (общий golden), а `double`, `BigDecimal` или `DateTime` в формате это ломают. Java и JS печатают некоторые `double` по-разному, а автоматическая сериализация в SDK — скрытое преобразование, от которого отказались в D24. Любая правка SDK к тому же даёт потребителям `pinned_drift` (D25), а точности не добавляет.

Вместо этого в `docs/sdk.md` зафиксированы соглашения поверх уже допустимых строк, целых и структур. Деньги — целые минимальные единицы с валютой, а когда их не хватает (ставки, курсы, точность выше 2⁵³) — десятичная строка. Чекер считает её через `decimal.Decimal` в режиме округления, который называет требование. Неденежные дроби — строка, чекер сравнивает их с допуском из spec, а не как строки. Время — целые миллисекунды от эпохи или ISO-8601 со смещением, дата — `YYYY-MM-DD`, длительность — целые мс, часовой пояс — имя IANA. Время, от которого зависит решение, приложение записывает в `data`: чекер часы не читает. Конкурентный сценарий тест записывает одним свидетельством — начальное состояние, операции с исходами и итог. Чекер ищет последовательный порядок, который объясняет эти исходы. Чекер по-прежнему проверяет каждую запись отдельно.

Формат, SDK, golden и runtime не меняются, новых зависимостей нет. Помощники разбора (`Decimal`, время) в `ebt_verification.api` появятся только по запросу проекта, как условлено в D24. Межзаписевый чекер над группой записей `scope` стоит рассмотреть отдельным решением, когда агрегированное свидетельство станут копировать несколько проектов или когда сценарий не поместится в одну запись. Дробь в формате — только если появится правило, где строки с допуском недостаточно.
(2026-11-01, статус: принято.)

### D29. Уровень наблюдения с контрактом наблюдения по умолчанию, мутационный аудит — исследование
Проверяется только записанное. Если решение принимается в двух местах, а запись стоит в одном, покрытие по инварианту и классам входов закрывают записи первого места, и гейт молчит. Предложение — уровень наблюдения (D17) по умолчанию и мутационный аудит — прошло ревью с условием: не обещать «дыра закрыта» и «решение доказано», а сравнить уровни на одинаковых дефектах. Пилот на копии replay-клона задачи пилота на TypeScript (материалы вне публичного репозитория) дал:
- пять заданных дефектов (второй путь, изменение после `ev()`, неприменённое решение, лишняя запись, мелькание окна) уровень решения не нашёл ни одного, OBS — четыре, OBS с журналом появлений окна — все пять;
- среди 124 мутантов кода применения уровень решения нашёл 1 нарушение, OBS — 57 нарушений и 12 дыр;
- 9 мутантов границ порядка нашёл только уровень решения;
- из 55 выживших 24 — логика сеанса. На трёх из четырёх проверенных пробой окно возвращается на следующем шаге того же сеанса, а сценарии OBS к этому моменту уже закончились.

Принято. Для требований с видимым или сохраняемым исходом новые проекты получают `<INV>-OBS` по умолчанию; проект на Dart не переводится (решение владельца 2026-10-29). Уровень решения остаётся для границ и как контроль целостности записи. Аналитик, кроме полей и помощников, пишет «Observation contract» для каждого `-OBS`: границу наблюдения; обязательные и запрещённые переходы (журнал появлений, если неверное состояние может появиться и исчезнуть до записи); момент завершения сценария и следующие шаги того же сеанса; запрещённые побочные эффекты (журнал вызовов подделок, если эффект не возвращается в наблюдаемое состояние). Тексты ролей ведутся в QA workflow вне публичного репозитория. Журналы — проектные помощники наблюдения, сверяемые через `pinned.txt`; SDK, формат, чекер ядра и runtime не меняются.

Гарантия формулируется так: OBS проверяет наблюдаемые последствия в заданных сценариях; мутационный аудит обнаруживает часть слепых зон этой проверки. «Мутант убит» означает чувствительность к этой порче на этих сценариях, а не доказанность решения. Выживший мутант — кандидат на разбор, а не готовый вывод. Процент убитых не равен доле решений со свидетельствами.

Мутационный аудит в гейт не входит. Прогон дорог: на 201 мутант — 10 минут в 4 потока и около 6 % шума под параллельной нагрузкой; разметка выживших делается вручную. Временные состояния и последовательности шагов автоматические операторы не порождают, поэтому для них нужны заданные дефекты. Аудит применяется как исследование одного требования с классификацией исходов: нарушение у чекера, дыра покрытия или формы, падение теста, ошибка запуска, выживание. Пропуски сеанса в пилотной задаче — находка для проекта, а не ошибка продукта. Новые сценарии и поля в его `spec.toml` утверждает человек (D4). Новый Runner API и обязательный `ev()` в каждой функции отвергнуты.
(2026-11-01, статус: принято.)

### D30. OBS по умолчанию закреплён в запуске ролей, журнал действия читается после него
Ревью D29 нашло две недоработки. Первая: «OBS по умолчанию» был только объявлен — `run_role.py` (QA workflow) по-прежнему подставлял тексты OBS лишь при `obs = true`, а процедура нового проекта этого не требовала. При исправлении выяснилось, что тексты `obs.toml` описаны только для TS: простое включение по умолчанию подставило бы Dart-проекту TS-инструкции. Поэтому в `obs.toml` перечислены языки с описанием (`langs = ["ts"]`). Без ключа `obs` уровень наблюдения включается для этих языков. Проект на другом языке обязан явно указать `obs = false` с причиной в комментарии, иначе запуск роли — отказ (код 2). `obs = true` для языка без описания — тоже отказ. Проект на Dart получил явное `obs = false` по решению владельца 2026-10-29; проект на TypeScript не меняется. Процедура нового проекта в QA workflow требует OBS и допускает отказ только с причиной.

Вторая: в пилоте журнал закрытия читался до закрытия. Окно, мелькнувшее во время или после закрытия, в свидетельство закрытия не попадало, а в сценарии, который закрытием заканчивается, его не проверял никто. Пилот повторён с журналом, который читается и после завершения действия (поле `appeared_after`, материалы пилота вне публичного репозитория, раздел 5):
- дефект «окно мелькает после закрытия из ленты» v1 пропустил, v2 нашёл в 4 из 4 закрытий из ленты;
- тот же дефект после любого закрытия v1 видел лишь косвенно, по следующей записи показа, а v2 — в 15 из 15 записей закрытия;
- D1–D5 по-прежнему ловятся;
- окно, мелькнувшее через 100 мс, то есть позже момента завершения (тихий интервал 50 мс), v2 не видит.

Контракт наблюдения в `obs.toml` теперь требует читать журнал записи действия после его завершения. Если важно и состояние до действия, журнал читается дважды. Момент завершения выбирается явно: изменение, запланированное позже него, не наблюдается.
(2026-11-01, статус: принято; уточняет D29.)

### D43. Self-test по элементам списков
Одного «убийства» на поле не хватало: self-test портил только первое скалярное значение внутри поля, поэтому чекер, читающий `items[0]` и игнорирующий остальные элементы, проходил проверку. Теперь self-test портит каждый элемент списка — первые 8 (`MAX_INDEX`), удаляя элемент и портя его содержимое, — и ведёт счётчики по полному пути `поле[i]…`/`поле.ключ`. В `self_test()` добавлен `weak_paths` — отсортированные пути, порча которых ни разу не поймана; `weak_fields` остаётся для потребителей и теперь выводится из `weak_paths`; `Report.weak_required` перечисляет пути, а у скалярного поля путь равен имени поля, поэтому прежние отчёты не меняются. Самопроверка не переставляет элементы списка: чекер законно сравнивает некоторые списки как множество.

`not_in_verdict` принимает имя поля, которое покрывает все его подпути, или путь с `[*]` (`lines[*].note`). Конкретные индексы не поддерживаются: путь нормализуется к `[*]`, поэтому исключение не привязывает отчёт к порядку элементов.

Следствие: проект может получить новый FAIL `weak_required` на поле-списке. Снимает его исправление чекера с целевым тестом на каждый элемент или запись пути в `not_in_verdict` после утверждения требования человеком (D4). В демонстрационном примере self-test нашёл в корректном свидетельстве `INV-SYNC-1` строки `remote`, удаление которых не меняло результат; чекер `sync_merge` при этом прав, поэтому в пример добавлено корректное свидетельство, где каждая строка `remote` влияет на результат, — проверку ради этого не ослабляли. Версия — `0.6.0`: меняется содержимое отчёта (`weak_paths`) и состав путей в `weak_required`.

Отказ формы учитывается отдельно от убийства логикой: в `fields[k]` и счётчиках путей появился `rejected` — число мутантов, на которых чекер ответил `WitnessError`; `killed` сохраняет прежний смысл (вердикт не ok или `WitnessError`), поэтому `rejected <= killed`. Пути, где все убийства — отказы формы (`killed == rejected`), перечисляются в `shape_only_paths` как сведения: в `weak_required` они не попадают и вердикт не меняют. Чтобы отличить проверку формы от сверки с правилом, self-test дополнительно подставляет значение поля верхнего уровня из первого другого образца того же инварианта, где оно отличается (путь — имя поля): подстановка другого допустимого значения ловится только логикой.

Подстановки считаются отдельно (`substituted`): путь слабый, только если на нём были обычные мутанты (`tried > substituted`), потому что подстановка сама слабости не создаёт. Иначе два корректных образца, различающиеся значением, которое законно не влияет на вердикт (например, `discount` `fixed:0` и `none:0` или один и тот же набор списка в разном порядке), дали бы ложный FAIL. Подстановка влияет только на `killed` и `shape_only_paths`, а `fields[k]` суммирует и `substituted`.
(2026-11-01, статус: принято.)

### D44. `ebt-gate --sync-pinned`
Копии SDK после каждой смены байтов (D27, D36) обновлялись вручную, и расхождение находил только гейт причиной `pinned_drift`. Команда `ebt-gate --sync-pinned <ebt-dir> [<project-root>]` разбирает `pinned.txt` так же, как `gate.sh`: пустые строки и строки с `#` пропускаются, первый токен — оригинал (`kit:` — из ресурсов установки, абсолютный — как есть, иначе относительно `<ebt-dir>`), второй — путь в проекте. `<project-root>` по умолчанию — текущий каталог; вывод — `обновлён <dest>` или `без изменений <dest>` по строке на копию. Код `0` — после выполнения все копии совпадают с оригиналами; код `2` — ошибка, ничего не записано.

Команда только копирует оригиналы по `pinned.txt` и не меняет проверку гейта: `pinned_drift` по-прежнему означает, что закреплённая копия не совпадает с оригиналом. Абсолютный путь назначения, выход за корень проекта (в том числе через `..` или symlink), строка с `\r` и повтор пути назначения отвергаются: гейт прочитал бы из CRLF путь с `\r` и искал бы копию не там, а две строки с одним путём дали бы молчаливую перезапись и затем `pinned_drift`. Все строки проверяются до первой записи, чтобы отказ не оставил половину обновлённых копий.
(2026-11-01, статус: принято.)

### D45. Гейт в GitHub Actions: недоверенные тесты и доверенная перепроверка
D26 оставлял вердикт и `gate.json` в досягаемости кода под проверкой: `test.sh` и `prepare.sh` исполняются от того же пользователя, что и гейт, и могут подменить итог. D34 привязывал `gate.json` к свидетельствам хешем, но согласованную подмену файлов и итога после вердикта нельзя было обнаружить. В CI нужен вердикт, выданный там, где код проекта не исполняется, и подпись, привязывающая `gate.json` к workflow основной ветки.

Проверка разделена на две стадии. `ebt-tests` запускается на `pull_request` и недоверенна: ставит проверенную поставку, запускает `ebt-gate` как обычно и выгружает `out/*.jsonl` и `gate.json` артефактом `witnessbox-evidence`. Её вердикт — только сведения. `ebt-verify` запускается на `workflow_run` и доверенна: GitHub всегда берёт этот workflow из основной ветки, поэтому ветка задачи не может его изменить. Код проекта во второй стадии не исполняется: `ebt/` извлекается из `BASE`, `prepare.sh` удаляется, вместо `test.sh` ставится replay-скрипт, который только отдаёт свидетельства из артефакта. Проверку выполняет настоящий `ebt-gate`; затем `gate.json` подписывается `actions/attest-build-provenance`, `gate.md` публикуется в summary, а на `head_sha` ставится commit status `witnessbox/gate` (`success` — PASS, `failure` — FAIL, `error` — ERROR или отказ до гейта). Логика — в composite actions `actions/setup` и `actions/verify`; установка witnessbox сверяется с `release.json` выпуска, а результаты второй стадии выгружаются артефактом `witnessbox-verdict`.

`pull_request_target` с исполнением кода PR отвергнут: он дал бы коду ветки write-токен и доступ к секретам. `workflow_run` не даёт ветке изменить workflow, потому что определение берётся из основной ветки. Артефакт первой стадии считается недоверенным: replay копирует только обычные файлы `out/*.jsonl` и не следует symlink, а `tests_exit_code` принимается только как целое 0 или 1; `EBT_REPLAY_DIR` — переменная второй стадии. Все `uses:` закреплены полным SHA (для сторонних actions — SHA коммита их репозитория, для actions WitnessBox — SHA коммита WitnessBox); runtime и Runner API не меняются.

Закрывается: вердикт и `gate.json` не изменяются кодом проекта; подпись привязывает `gate.json` к workflow основной ветки; spec и `checks.py` берутся из `BASE`, поэтому правка `ebt/spec.toml` в ветке даёт FAIL `protected_paths_changed`, а не PASS по spec ветки. Не закрывается: свидетельства по-прежнему пишет код под проверкой, а `tests_exit_code` первой стадии — заявление этого кода, как и при локальном запуске; намеренный обход в первой стадии (фоновый процесс, `PATH`, `~/.gitconfig`) не ловится. PR из форков в первой версии не поддерживаются: у `workflow_run` для них нет `pull_requests[].base.sha`, поэтому статус — `error`, а не `success`. Аттестации в приватных репозиториях требуют тарифа GitHub с поддержкой artifact attestations.

### D47. `ebt-gate --check-only` и `ebt-gate --test-checks`
Ошибки подключения — неверная `spec.toml`, неисполняемый `test.sh`, `pinned_drift` — выяснялись только после полного прогона, а тесты проектного чекера запускались обходным рецептом с интерпретатором из `--installation` (D32). Добавлены две ветки `ebt-gate`.

`--check-only <ebt-dir> <clone>` повторяет предварительные проверки гейта, не запуская `prepare.sh`, `test.sh` и чекер по свидетельствам: разбор `spec.toml`, загрузка `checks.py` и регистрация каждого чекера спецификации, `known.toml`, `baseline.jsonl`, правила выбора runner из `gate.sh`, `pinned.txt` (разбор общий с `--sync-pinned`), чистота клона и скрытые правки `skip-worktree`/`assume-unchanged`, а при `BASE` — изменения защищённых путей `ebt/` и `tool/ebt_check/`. Коды: `0` — проблем нет, `1` — найдены проблемы, `2` — ошибка вызова. Это подсказка, а не вердикт: гарантирована только связь «проблема → гейт на том же входе не даёт PASS», обратное не обещается — тесты и свидетельства команда не проверяет. `checks.py` импортируется так же, как в чекере: это доверенный проектный код (docs/extensions.md). Файлы не меняются, а без `BASE` вывод прямо говорит, что защищённые пути не проверялись.

`--test-checks [<ebt-dir>]` запускает `unittest` интерпретатором поставки. Нулевой прогон (`Ran 0 tests`) — код `1`, а не успех: иначе отсутствие тестов выглядело бы зелёным. Рецепт D32 из `test_checks.py`, README заготовки и `docs/scaffold.md` заменён этой командой.

Обе команды — совместимое расширение поддерживаемого интерфейса, версия `0.7.0`. `gate.sh` и формат `gate.json` не менялись.

### D48. Стек `generic` и сквозные примеры в CI
Подключение проекта, чей инструмент тестов не совпадал с шаблонами `dart`, `ts` и `jvm`, требовало переписать `test.sh`, а сквозной путь «установка → заготовка → `--sync-pinned` → PASS → дефект → FAIL» проходил только вручную в демо-репозитории приёмки D45. D19 оставлял пример полного подключения отложенным; теперь он есть в самом репозитории и исполняется на каждый PR.

Добавлен стек `generic`: `test.sh` запускает обязательную `EBT_TEST_CMD`, копирует свидетельства из `EBT_EVIDENCE_DIR` (по умолчанию `build/ebt`) и отображает коды команды так: `0` → `0`; код из `EBT_TEST_FAIL_CODES` (по умолчанию `1`) → `1`; остальное → `2`. Слова `EBT_TESTS` передаются команде отдельными аргументами через `"$@"`, без `eval`. Это закрывает npm/Jest, pnpm/Vitest, Maven и `dart test` без правки шаблона; для TypeScript SDK с Jest нужна подстановка `MODE=test`, а Maven и Gradle возвращают `1` и на сломанную сборку, поэтому точное различение остаётся за проектом и описано в `docs/scaffold.md`. Рецепта pytest нет: Python SDK не поставляется, подключение Python-проекта ждёт отдельного решения о Python SDK (план `2026-11-02-sdk-conformance.md`).

Примеры `examples/e2e/ts` и `examples/e2e/jvm` реализуют правило шаблонной spec (`REQ-EXAMPLE-1`, `value × 2`) с классами `zero`, `positive`, `negative`, поэтому `spec.toml`, `checks.py` и `test_checks.py` берутся из заготовки без изменений и проверяется заготовка целиком. Шаблонная spec остаётся примером, а не утверждённой спецификацией (D4): в примерах она — фиксированный тестовый вход. Драйвер `examples/e2e/run.sh` собирает временный git-репозиторий, генерирует Gradle wrapper нужной версии, прогоняет `--sync-pinned`, `--test-checks` и `--check-only` (если установленная поставка их знает), получает PASS на корректном коде и FAIL с `checker_failed` после дефекта. Gradle wrapper и `node_modules` генерируются во временном репозитории и не коммитятся. CI-задача `e2e` запускает драйвер для `ts`, `generic` и `jvm`; `make test` по-прежнему не требует сети и Bun/Gradle. Версии закреплены точно: Gradle `9.8.2`, JUnit `5.14.4`, Vitest `5.0.5` (в `bun.lock`), actions — по SHA.

Демо-репозиторий D45 этими примерами заменён: приёмка CI-режима остаётся его историческим доказательством, но новые изменения проверяются здесь. Версия — `0.7.0`.
(2026-11-02, статус: принято.)



### D47-уточнение. Граница `--check-only` с гейтом (ревью 0.7.0)
Ревью ветки 0.7.0 воспроизвело шесть входов, где `--check-only` возвращал `1`, а гейт — PASS, то есть нарушалась гарантия D47. Причины разделились.

Незарегистрированный чекер в спецификации проходил, если у его инварианта не было записей или он был вне `EBT_INV`: `NO_CHECKER` возникал только при проверке записи. Теперь `ebt-check` перед разбором свидетельств требует, чтобы каждый `checker` из `spec.toml` был в `CHECKERS`; неизвестный чекер — код `2` (ERROR), а не молчаливый PASS. Проверка общая для `ebt-check` и `--check-only`; при заданном `EBT_CHECK` `--check-only` не судит о регистрации по локальному реестру, потому что внешний чекер может знать свои чекеры.

Остальные пять входов — строгие проверки `read_pinned`, унаследованные от `--sync-pinned`, которых гейт не делает: `\r` или не-UTF-8 в строке-комментарии, абсолютный `dest`, `dest` вне клона (`../x`) и повтор `dest` при совпадающей копии. `--check-only` теперь разбирает `pinned.txt` в режиме `gate_rules=True`: комментарии пропускаются до любых проверок, абсолютный и относительный `dest` вне клона и повтор разрешены, сравнивается только содержимое. Строгие правила остаются у `--sync-pinned`: он пишет файлы и обязан отвергать неоднозначный путь.

Закрыты и обратные расхождения, где `--check-only` отвечал `0`, а гейт — ERROR: репозиторий без коммитов (нет `HEAD`), `EBT_CHECK`, указывающий на несуществующую команду, и `EBT_INV` с неизвестным инвариантом. Все три теперь дают проблему соответствующей проверки.

В `generic/test.sh` команда из `EBT_TEST_CMD` нормализуется перед запуском: хвостовые переводы строк и комментарий в конце строки отбрасываются, а если команда сама ссылается на `"$@"`/`"$*"`, слова `EBT_TESTS` приходят позиционными параметрами и не добавляются второй раз. Тест-пробелы закрыты: добавлены случаи A–F, обратные случаи, проверка свидетельств в `OUT_DIR` при коде `7` и краевые случаи `EBT_TEST_CMD`.

`gradle/actions/setup-gradle` в CI переведён с `v6.4.1` (5 дней на момент ревью) на `v6.4.0` (2026-09-28), чтобы выполнялось правило «не моложе двух недель». Версия поставки остаётся `0.7.0`: она ещё не выпущена.
(2026-11-02, статус: принято.)

### D47-уточнение 2. Регистрация чекеров, внешний `EBT_CHECK` и `generic`
Первое уточнение D47 сделало незарегистрированный чекер ошибкой запуска `ebt-check` (код `2`). Это меняло публичные коды чекера и вердикт гейта сильнее, чем нужно: сценарий, где утверждённая spec уже содержит инвариант, чекер которого ещё не написан, а задача ограничена другим `EBT_INV`, начинал давать ERROR. Уточнение отменяет это в пользу находки в отчёте.

Теперь `NO_CHECKER` для инварианта в scope добавляется в отчёт `build_report` ещё до разбора записей, если записей для него нет; если запись есть, находку даёт `check_record`. Код выхода остаётся прежним: `1` (FAIL) для критичной находки, `0`/`2` не меняются. Инвариант вне `EBT_INV` с ненаписанным чекером не валит прогон, пока нет записи с этим инвариантом; `--check-only` сообщает о такой проблеме только для инвариантов в scope. Так сценарий «spec опережает код, задача в другом инварианте» снова работает, а гарантия «проблема `--check-only` → не-PASS» сохраняется.

`--check-only` при заданном `EBT_CHECK` больше не разбирает локально `spec.toml`, `checks.py`, `known.toml` и `baseline.jsonl`: внешний чекер может понимать их иначе, и локальная проблема нарушала бы гарантию (проверено: падающий `checks.py` при внешнем чекере, который отвечает `0`, давал PASS гейта при проблеме подсказки). Проверяются только части, не зависящие от чекера: наличие `spec.toml`, существование `EBT_CHECK`, runner, `pinned.txt`, клон и `BASE`; отсутствие внешней команды — проблема.

В `generic/test.sh` самописный разбор shell убран: он не покрывал хвостовые `;`/`&`/`|`/`\`, позиционные `$1…$9` и сложные кавычки. Вместо разбора команда должна быть простой; если в ней есть `#`, `;`, `&`, `|`, `\` или `$1…$9`, она обязана сама ссылаться на `"$@"`/`"$*"`, иначе `test.sh` возвращает код `2` с сообщением. Простая команда получает слова `EBT_TESTS` отдельными argv; сложный сценарий оформляется скриптом. Это закрывает класс ошибок «аргумент выполнился отдельной командой / потерялся», а не отдельные примеры.

`docs/architecture.md` описывает `NO_CHECKER` как FAIL, в том числе для инварианта в scope без записей. Версия остаётся `0.7.0`.
(2026-11-02, статус: принято.)

### D47-уточнение 3. `--allow-uncovered` и краевые случаи аргументов
`D47-уточнение 2` говорит, что коды `ebt-check` не меняются, но это не совсем так для `--allow-uncovered`: если в scope есть инвариант без чекера и без записей, до исправления флаг скрывал дыру покрытия и давал `0`, а теперь `NO_CHECKER` — критичная находка и код `1`. Это осознанное следствие: инвариант задачи нельзя считать покрытым, если проверять его нечем. Гейт `--allow-uncovered` не передаёт, поэтому его вердикт это не затрагивает; `--check-only` про флаг не знает и сообщает о проблеме.

Обратное расхождение остаётся и не обещается D47: инвариант вне `EBT_INV` с неизвестным чекером и записью даст гейту `NO_CHECKER` (FAIL), а `--check-only` — `0`, потому что свидетельств не читает. Чтобы закрыть его, пришлось бы снова менять вердикт гейта или читать свидетельства в подсказке; ни то, ни другое не входит в D47.

### D53. `ebt.dart` устойчив к dart format
Проект на Dart копирует `ebt.dart` байт в байт (`pinned.txt`), а его CI может проверять `dart format --set-exit-if-changed`. Файл 0.7.0 оставался неизменным только в коротком стиле при ширине 80. Tall-стиль (Dart 3.7+) и ширина 100–120 склеивали сигнатуры, геттеры и вызовы. Отформатировать копию нельзя — это `pinned_drift`, исключать её из форматтера должен каждый проект отдельно.

Принято: каждый оператор `ebt.dart` занимает одну строку короче 80 символов, длинные выражения разбиты на локальные переменные. Тогда ни одному стилю при ширине 80–120 нечего склеивать или переносить. Сигнатура `ev()` в одну строку не помещалась, поэтому появился публичный `typedef EbtData = Map<String, Object?>`, а `data` стал `EbtData?` без значения по умолчанию; `null` записывается как `{}`. Для вызывающих это совместимо: прежние вызовы компилируются и пишут те же байты, golden не изменился. `// dart format off` в начале файла остаётся страховкой для tall-стиля на случай, если форматтер начнёт менять не только переносы. Короткий стиль эту страховку не читает. `make format-dart` входит в `make test-sdk`, поэтому выполняется в CI по PR и в `make release-check`. Он прогоняет `dart format --set-exit-if-changed` по выпускаемому `ebt.dart` в шести сочетаниях: `--language-version` 3.6 и `latest`, ширина 80, 100 и 120. Тот же прогон повторяется без `// dart format off`, чтобы страховка не скрывала перенос в коде. Изменение стиля в новой версии Dart проявится на выпуске поставки, а не в CI проекта.

Байты `ebt.dart` изменились: проекты на Dart один раз обновляют закреплённую копию из `resources` новой установки, до этого гейт даёт `pinned_drift`. Формат свидетельств, golden, сообщения об ошибках и поведение остальных SDK не меняются.
(2026-11-09, статус: принято.)

### D58. Страница спецификации
Человек утверждает спецификацию (D4), читая `spec.toml`. В TOML текст требования перемешан с техническими полями, и ничто не привязывает утверждение к одной версии файла: правка после утверждения незаметна, пока кто-то не сравнит файлы. Инструкция агенту (D50) предлагала показывать черновик обычным текстом в чате.

Принято: подкоманда `witnessbox spec <spec.toml> <out.html>` пишет самодостаточную HTML-страницу: требования с `source`, инварианты с `statement`, `checker`, `witness`, `partitions` или переходами, пометки для требования без `source` и без инвариантов и полный `sha256` файла, первые 12 символов которого выделены так, как их печатают гейт и отчёт чекера. Спецификация проверяется `load_spec` чекера; неверная спецификация даёт код `2` и не даёт страницы. На странице нет скриптов, и она ничего не загружает из сети. Гейт пишет такую же страницу для проверенной копии спецификации в `<run-dir>/spec.html` и ссылается на неё из `gate.md`, так что каждый вердикт называет спецификацию, по которой он вынесен. Если спецификация не разбирается, вердикт и так — ошибка чекера: страница не пишется, и `gate.md` об этом сообщает. `spec.html` — новое имя в `files` у `gate.json`, совместимое изменение формата 1. Этап 2 инструкции агенту показывает черновик этой страницей и просит человека утвердить напечатанный хеш. Страница предназначена человеку, как `gate.md`: её текст не интерфейс.

Код — новый модуль `spec_page.py` (входит в `checker_sha256`) и изменения в `cli.py` и `gate.sh` (входят в `gate_sha256`): оба отпечатка меняются, поэтому изменение выходит со следующим выпуском. Эта запись версию не поднимает.
(2026-11-11, статус: принято.)
