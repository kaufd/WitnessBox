# Заготовка `ebt/` для нового проекта

Установленная поставка умеет создать каталог проверки нового проекта:

```bash
ebt-gate --scaffold <dart|ts|jvm> [<каталог>]
```

`<каталог>` по умолчанию — `ebt` в текущем каталоге; `.` заполняет текущий
пустой каталог. Существующий непустой каталог команда не трогает: она отказывается
писать поверх утверждённой `spec.toml` и возвращает код `2`. Шаблоны входят в wheel и sdist (`witnessbox/resources/scaffold/`);
исходники репозитория после установки не нужны.

Стеков три; они различаются `test.sh` и строкой `pinned.txt`:

| Стек | Проект | `test.sh` по умолчанию | SDK |
|---|---|---|---|
| `dart` | Dart/Flutter | `flutter test --no-pub test/ebt` | `lib/ebt/ebt.dart` |
| `ts` | TypeScript/Vite/Vitest | `bunx vitest run .ebt.test` | `src/lib/ebt/ebt.ts` |
| `jvm` | Java/Kotlin на Gradle | `./gradlew test --tests '*EbtTest'` | `src/test/java/ebt/Ebt.java` |

## Что создаётся

| Файл | Назначение |
|---|---|
| `spec.toml` | пример `[req]`/`[inv]` с комментариями; заменяется утверждённым требованием |
| `checks.py` | пример независимого чекера и реестра `CHECKERS`; не импортирует приложение и SDK |
| `test_checks.py` | тесты примера чекера: корректный случай, каждый класс входов, нарушение, ошибка формы |
| `test.sh` | запуск тестов выбранного стека и сбор свидетельств в `OUT_DIR` |
| `pinned.txt` | закрепление копии SDK (и, при необходимости, помощников наблюдения) |
| `README.md` | та же инструкция для человека в каталоге проекта |

`spec.toml`, `checks.py` и `test_checks.py` одинаковы у всех стеков. `test.sh` и
`pinned.txt` берутся из каталога стека.

## После создания

1. **Утвердить требование.** Заменить `REQ-EXAMPLE-1` и `INV-EXAMPLE-1` в
   `spec.toml` утверждённым требованием, указать `source`. В подключающем проекте
   спецификацию утверждает человек (D4); агент, пишущий код приложения, её не
   меняет. `witness` — минимальный набор входов и выходов для пересчёта,
   `partitions` — реальные классы входов из требования, а не перечень тестов.
2. **Реализовать чекер.** `checks.py` пересчитывает результат по `witness` и
   возвращает `Verdict`; некорректная форма свидетельства — `WitnessError`.
   Проверка чувствительности — `ebt-check --self-test`. Тесты чекера из корня
   проекта запускайте интерпретатором поставки: пакет из `uv tool install` не виден
   системному `python3`.

   ```bash
   python=$(ebt-gate --installation | python3 -c 'import json, sys; print(json.load(sys.stdin)["python"])')
   "$python" -m unittest discover -s ebt -p 'test_checks.py'
   ```

   Системный `python3` в этой команде только читает JSON из `--installation`.
3. **Скопировать SDK.** Из корня проекта выполните `ebt-gate --sync-pinned ebt`
   (подставьте имя каталога, если он другой): команда разбирает `pinned.txt` так же,
   как гейт, берёт `kit:`-файлы из ресурсов установленной поставки и копирует
   оригиналы в проект. Копия должна совпадать байт в байт, иначе гейт даст
   `pinned_drift`; после обновления поставки та же команда обновляет изменившиеся
   копии. Абсолютные пути назначения и выход за корень проекта (в том числе через
   `..` или symlink) команда отвергает.
4. **Написать тесты свидетельств.** Они водят реальный код по классам входов и
   пишут JSONL в `build/ebt/<feature>.jsonl` (формат — [SDK](sdk.md)).
5. **Добавить `prepare.sh`, если нужны зависимости.** Для чистого клона это
   `flutter pub get`, `bun install --frozen-lockfile` или ничего для Gradle.
   Гейт запускает `prepare.sh` до `test.sh`; шаблон `test.sh` предполагает
   зависимости уже установленными.
6. **Запустить гейт** с `BASE` и `EBT_INV` задачи. Пока свидетельств нет, гейт
   завершается кодом `2` (ERROR) — это отсутствие проверки, а не PASS. Каталог
   `ebt/` коммитится в репозиторий проекта до задачи: с `BASE` изменение `ebt/`
   в ветке задачи гейт считает нарушением защищённых путей.

## Договор `test.sh`

- Рабочий каталог — корень чистого клона; гейт проект не копирует.
- `OUT_DIR` — пустой абсолютный каталог результатов; свидетельства пишутся в
  `OUT_DIR/*.jsonl`, разные файлы могут начинать `seq` с 1.
- Слова `EBT_TESTS` передаются аргументами; без них шаблон запускает только тесты
  свидетельств.
- Код `0` — тесты прошли, `1` — тесты выполнились и упали, остальные коды — ошибка
  исполнения. Свидетельства проверяются и при коде `1`, поэтому шаблон копирует их
  при любом исходе.
- `test.sh` исполняется с правами гейта; `OUT_DIR` — не песочница.

Шаблоны рассчитаны на macOS `/bin/bash` 3.2: без `${var,,}`, пустых массивов под
`set -u` и конструкций Bash 4. Для другого инструмента (Maven, pnpm, чистый
`dart test`, Android-модуль) меняются команда, путь свидетельств и разбор кодов
выхода; договор гейта сохраняется. Для Android в `jvm`-шаблоне задайте
`EBT_GRADLE_TASK=:app:testDebugUnitTest`, `EBT_GRADLE_RESULTS=app/build/test-results/testDebugUnitTest`
и `EBT_EVIDENCE_DIR=app/build/ebt`.

## `pinned.txt`

Строка — `<оригинал>  <путь в клоне>`:

- `kit:lib/ebt/…` — файл из ресурсов установленной поставки; так закрепляется SDK;
- `obs/<feature>…` — файл рядом с `ebt/`; так закрепляются помощники наблюдения (D29);
- абсолютный путь — внешний файл.

Копия должна совпадать с оригиналом. Отличие или отсутствие файла — причина
`pinned_drift` и FAIL гейта. Путь назначения в шаблоне — пример; поставьте тот,
куда проект кладёт SDK.

## Границы

Заготовка — пример, а не утверждённая спецификация и не доказательство поведения.
Она не создаёт `known.toml`, `baseline.jsonl` и `prepare.sh`: они появляются по
потребности проекта. Гейт проверяет только записанное; решение, принятое в коде без
свидетельства, останется вне проверки.
